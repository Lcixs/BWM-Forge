# CodeWM Blender session instructions

This file contains the common developer instructions for the current Codex SDK modeling session. The host runs `scene_only -> robot_only -> composed`. The three stages share one Codex session; each call completes only one round of the assigned stage. The host controls stage order, previews, `accept/revise/quit` feedback, white-model video rendering for each composed round, and publication of the accepted `final.blend` and video. There is no separate `register` or `final` modeling stage. Do not advance stages yourself or claim acceptance checks the host has not performed. Write reports, progress messages, and user-facing explanations in English; preserve required identifiers and enum values.

## Execution boundaries

- Save each round's project only to the `.blend` path specified in its stage prompt. Place task-specific bpy scripts in that round's assigned `scripts/`; the source directory `Blender/scripts/` is for reusable tools. Store supporting images, diagnostics, and logs in the assigned `evidence/`, and the round overview in `report.json` at the full path supplied by the host.
- `scene_only` builds only the scene and `camera_input`, without the robot. `robot_only` builds only the complete URDF model and `camera_robot_preview`, without the scene. `composed` merges copies of both accepted projects, aligns the reference frame, and animates motion. Accepted upstream `.blend` files are read-only. Revision rounds continue from the previous project for that stage rather than rebuilding completed work from an empty scene.
- The robot-only project is a reusable standalone asset: use a task-independent default configuration and create no task animation. Task-specific root placement, initial pose, camera refinement, and motion belong to `composed`. Never modify or publish asset-library caches yourself; the host copies the accepted robot-only project into the library after feedback.
- Actually execute Blender scripts and save the project. The host opens stage projects in a separate Blender process, checks minimum structural requirements, and renders previews. After the automatic review of each composed round, the host renders its full white-model video before collecting user feedback. On acceptance, the same project and video are published without rendering again, then the host separately requests a GPT stage summary. Video rendering does not call a model. Successful preview rendering does not establish visual, kinematic, or physical validity.
- The host uses monochrome Workbench rendering for white-model previews and the final video; do not rewrite original robot materials for this purpose. Preserve the reference aspect ratio for scene and composed outputs, with a default minimum short side of 720 pixels.
- Use bpy APIs supported by the installed Blender version. Before using a World in an empty scene, check for one and create it if needed. If execution fails, inspect logs, fix the script, and rerun it. A written script alone is not evidence that a project was generated.
- For Windows commands, prefer the execution tool's `shell=cmd.exe` option when supported; do not wrap cmd inside a failing PowerShell process. For process initialization failures, perform minimal diagnostics and try a shell without profiles or another supported execution entry point with the same permissions. Continue only after it succeeds. Do not repeat identical errors without a reason. Never bypass explicit permission denials or failed approvals; preserve diagnostics and explain unfinished work.

## Evidence and geometry

Determine reference authority by entity and property. The task defines retained, replaced and excluded entities; the selected URDF defines target identity and structure. Images and inspected video frames support visible geometry and relationships; supplied trajectories support motion under their declared conventions. Keep conflicts and unsupported assumptions explicit. Do not present uncalibrated cameras, invisible dimensions, hidden bases, unknown component calibration, or proxy geometry as measured. Preserve original images/video, URDF, available Parquet/NPZ, and accepted upstream projects.

First fit the visible overall perspective, composition, object outlines, and pairwise relationships. Then complete the minimum plausible geometry hidden by the target or other occluders using visible boundaries, support, repetition, or symmetry. Empty semantic labels or flat proxies cannot replace task objects, targets, container cavities, thickness, or occlusion depth. Classify each key object as `observed`, `supplement_supported`, `constrained_completion`, `generic_hypothesis`, or `unresolved`; record evidence, unknown fields, and mesh identity. If identity, reference pose, task-relevant surfaces, or target containment/support remain speculative, contact and task completion are only assumption-based diagnostics. User acceptance of a preview does not promote an assumption to an observation.

Check source aspect ratio, crop, perspective, directed object offsets, principal axes, outlines, occlusion, and shared support together. Do not force square references into 16:9 or claim alignment from camera names or unchanged matrices alone. When a change improves only local metrics, compare overall composition and relationships for regressions and retain the better previous candidate.

## Robot and reference-frame registration

Use the task URDF and original meshes, preserving one continuous hierarchy, joint origin/axis/type/limit/mimic, metric link scales, and actual modeled mechanisms. Retain invisible proximal links and the base. An unseen base may remain unsupported and must be labeled inferred. If a robot is visible, do not reverse its visible pose to invent mounting support.

Establish a consistent metric world only in the composed copy. Express the robot pose through one root/base transform, legal joints, and the same FK chain. If the robot is visible, inspect crop boundaries, the directed link/joint relationships, target heading, link foreshortening and self-occlusion, task-object relationships, and depth occlusion before inferring whether it enters from the camera, background, left, or right. Otherwise design a plausible task-compatible configuration and label it inferred. Bounding-box or component centers, text-implied mounting planes, disconnected per-link movement, mirroring, or hidden meshes cannot establish correct registration. If source-camera correspondence conflicts with avoiding walls, revisit scene depth, shared scale, and root/joint/IK assumptions; do not move locked cameras or scene objects to hide errors.

For image keypoints or masks, reconcile the source image's top-left origin with Blender projection coordinates. Update the view layer/depsgraph before projecting and read transforms from evaluated objects. Sparse vertex projections are only for initialization or diagnostics; assess visibility using rendered silhouettes, ID/alpha masks, or equivalent complete mesh rasterization. An empty candidate mask where the robot should be visible is not a low-error match. Call a procedure optimization only if a multistep parameter solve was actually executed and parameter/cost records were retained.

## Motion, contact, and checks

Align frame 1 before fitting motion, and preserve that alignment when the final Action/F-Curves are evaluated at frame 1. Do not call task-generated motion measured. Build states and transitions required by the task using actual modeled mechanisms and continuous legal motion. Coordinate world-root motion and internal joints when needed. Check applicable contact, support and clearance; do not assume a gripper or fixed action sequence. Parenting or constraints alone are not contact evidence.

## Evidence by input type

### Type 0: First frame and task description

The reference is the input first frame. No robot trajectory is supplied. Infer subsequent motion from visible initial state, URDF, scene, and task text, and document inference boundaries. Do not invent a video timeline, Parquet, NPZ, or native sampling rate.

### Type 1: First frame and Parquet/NPZ trajectory

The reference is the input first frame. Down-weight, retarget, or ignore trajectory coordinates or motion that conflict with the frame and task. Preserve original files, hashes, sample order, and known native timing. Distinguish native sampling speed from 30 FPS display interpolation. Blender Python uses the host conversion report and NPZ/JSON; it must not read raw Parquet directly.

Follow the actual `motion` convention in `input.json`: read the NPZ `action` array or Parquet `action` column. Interpret only declared columns. For joint input, each column corresponds to the joint at the same position in motion.joint_names; there is no additional gripper column. Tool joints are included only when explicitly named. EEF input is supported only for robot arms and uses xyz, roll/pitch/yaw, and a gripper channel. These are user-provided absolute states, not deltas or velocities. Format validation does not establish measured provenance. Row i occurs at i/motion.fps seconds; interpolation must preserve the first-to-last sample duration. For a declared gripper channel and an actual gripper, preserve raw values without clipping or renormalization; 0 closed and 1 open are convention references only. Use actual URDF drives and mimic relationships and document unsupported channels or unknown calibration.

### Type 2: Demonstration video

The reference is extracted from the first video frame. Also inspect later key moments, action order, contact, and object-state changes. Distinguish source operations from robot-executable motion. If the target robot is absent, do not claim to observe its pose or joint trajectory. No robot trajectory is supplied; label mapped configurations and motion as inferred and document their basis and uncertainty.

## Common checks and feedback

An explicit user request for a new camera view overrides original-frame camera matching for that composed revision and its review. Continue from the previous composed project; preserve scene geometry, robot placement and joint states, object transforms, animation, timing, and resolution unless the user explicitly requests changes to them. Adjust the camera only, including its animation when needed. Judge framing against the requested view; never restore the original view or move scene objects to make the image resemble the original reference. Later revisions inherit the latest requested view until the user changes it again.

After the host renders a round preview, it may request one quick review of that same round before user feedback. On this call, follow the review prompt's bounded sampling and correction scope, update the existing report, and leave unchecked issues explicit. Do not restart modeling, start another review cycle, or claim user acceptance.

Check the saved and reopened project at the first frame, semantic keyframes, task-relevant contact/state transitions, final frame, and sparse samples elsewhere. Add checks around velocity/acceleration peaks, direction reversals, nearest obstacles, component transitions and kinematic branch risks. Use swept capsules/AABBs/meshes or equivalent broad-phase checks between adjacent samples to detect possible tunneling, with local refinement only in risky intervals. Bounded shallow local intersections are acceptable only at designed adjacent-link seams, intended task contact and support patches. Crossing an obstacle's full thickness, entering a closed object, penetrating collision cores, sustained intersection of multiple nonadjacent links, or tunneling between samples are serious penetrations. IoU, bounding boxes, overlap volume, or nearest distance alone cannot downgrade them. Mark unchecked matters unknown; do not claim formal continuous-collision proof.

After feedback, edit only the current stage's permitted copies and scope. Recheck affected first frames, keyframes, and physical relationships. Record actual evidence, changes, checks, and unresolved issues. Do not substitute earlier previews or PASS fields for current checks, or generate experience-application reports or cross-task experience candidates.


Use actual URDF hierarchy and geometry rather than asset names to determine mechanisms. Preserve target structure and link dimensions. Determine retained, replaced and excluded entities from the task; do not force target anatomy to match a different source actor. Treat observations, supplied motion and generated inference separately. Do not impose a particular robot anatomy or behavior.
